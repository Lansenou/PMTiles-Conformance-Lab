# Release workflow

Implemented in `.github/workflows/ci.yml` (job `release`). This replaces the earlier proposal of a manually dispatched draft release: the owner decided that every successful push to `main` publishes a release automatically.

## When a release is published

* Trigger: a `push` to `main` (in practice, merging a pull request). Pull requests never publish: the `release` job is skipped unless `github.event_name == 'push'` and `github.ref == 'refs/heads/main'`, and only that job has `contents: write`.
* Gates: `release` needs the `check` (Linux), `windows` and `macos` jobs of the same workflow run, so it runs only after all three passed for that exact commit.
* Concurrency: pull request runs cancel superseded runs of the same ref; runs for pushes to `main` are never cancelled (`cancel-in-progress` is true only for `pull_request`), so a push waiting for its release is not dropped by a later push.

## Version rule

* CLI release version: `v0.4.<N>`, where `<N>` is `github.run_number` of the `ci` workflow run for that push. Run numbers only grow, so versions are monotonic. Gaps are expected: pull request runs and failed main runs also consume numbers.
* The version is embedded in the binaries (`-X main.version=v0.4.<N>`) and printed by `pmtiles-lab version`. Pull request builds are labelled `dev-<sha>`; local builds `dev`.
* The fixture generator version (`fixtures.Version`, currently 0.4.0, recorded in `manifest.json`) is separate. It changes only when generated bytes change, and `pmtiles-lab version` prints both: `pmtiles-lab v0.4.57 (fixtures generator 0.4.0, PMTiles spec v3.6@8b8ddea)`.
* Moving to another minor series (0.5.x) is a one-line change of the `VERSION` expression in `ci.yml`.

## What is published

Built once by the `check` job and handed to `release` as a workflow artifact, so the published files are the ones that were checked and smoke-tested:

| File | Content |
|---|---|
| `pmtiles-lab_v0.4.N_linux_amd64`, `_linux_arm64`, `_darwin_amd64`, `_darwin_arm64`, `_windows_amd64.exe` | `CGO_ENABLED=0 go build -trimpath -ldflags="-s -w -buildid= -X main.version=v0.4.N"` |
| `pmtiles-lab-fixtures_v0.4.N.tar.gz` | `fixtures/` (tar sorted by name, owner 0, mtime 0, `gzip -n`) |
| `SHA256SUMS` | SHA-256 of the six files above; check with `sha256sum --check SHA256SUMS` |

`scripts/build-release.sh VERSION OUTDIR` produces exactly these files locally. The Go version comes from `go.mod` (`go-version-file`), so the same toolchain rebuilds the same bytes.

## Checks before publishing

* `check` (ubuntu-latest): `scripts/check.sh` (gofmt, vet, tests, `-race`, fixture regeneration diff, the `verify/` module with independent decoders, fuzz smoke), then the five binaries are built, each is confirmed as `CGO_ENABLED=0` from its build info, and the linux/amd64 binary runs `scripts/smoke.sh`.
* `windows` (windows-latest, autocrlf checkout): `SKIP_RACE=1 scripts/check.sh`, then a native `CGO_ENABLED=0` windows/amd64 build runs `scripts/smoke.sh`.
* `macos` (macos-latest, Apple silicon): a native `CGO_ENABLED=0` darwin/arm64 build runs `scripts/smoke.sh`. If the runner has Rosetta 2, the darwin/amd64 build is smoke-tested too; otherwise the log says it was not launched.
* `scripts/smoke.sh` runs `version`, `generate` (diffed with `fixtures/`), `inspect`, `probe`, `tilecheck` on the local PMTiles file, then starts `serve` and `serve-xyz` on loopback ports and runs `tilecheck` over HTTP ranges and over TileJSON/XYZ, and confirms that a non-MBTiles file is rejected.
* linux/arm64 is cross-compiled and checked for its target and CGO setting, but not launched in CI.

## Idempotence and tags

* An existing tag is never moved. If `v0.4.N` exists at a different commit, the job fails.
* A rerun of the same workflow run has the same run number, so it targets the same tag. If the release already exists, the job re-uploads the same asset names (`--clobber`) and makes sure the release is published; otherwise it creates the release and its tag at `GITHUB_SHA`.
* Releases are created with `--latest=false` and then marked latest only if no higher `v0.4.x` release exists, because runs can finish out of order.
* No third-party release actions: the job uses the preinstalled GitHub CLI with the workflow token. `actions/checkout`, `actions/setup-go`, `actions/upload-artifact` and `actions/download-artifact` are pinned by commit SHA.

## Not done

* No signing or artifact attestations.
* No package registry, container image or deployment.
* Automatic publication can only be observed after a merge to `main`; pull request runs exercise every step except `release`.
